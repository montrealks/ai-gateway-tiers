Getting the apps onto the router

Migration plan — 8 August 2026 · four consumers, one dispatcher · kboodle deliberately excluded

The router works. Nothing uses it. This is the plan for moving each consumer across — written after reading every call site, which changed the answer in three places: one app should not migrate, one can only migrate halfway, and the "shared Python client" turns out to have eight downstream repos rather than one.

Verified live while writing this, 8 Aug 2026: /health returns {"ok":true}; /v1/tiers returns five tiers whose chains are byte-identical to tiers.json in git, so KV is currently in sync; five per-app tokens exist in app-tokens.txt.

Also worth noting: three defects from the architecture review are already closed — per-app tokens (#4), /v1/embed (#5) and streaming (#6) all shipped. Defect #1 (no client fallback) has not, and it shapes the sequencing below.

Should this wait on the client fallback?

Step 1 may go first without it. Everything after step 1 should wait.

route1views is the one consumer where a router outage is already a modelled, tested state: every one of its three call sites treats a null from LlmService::complete() as normal. Title/content/category suggestions are optional UX that silently disappears, and the spam classifier on the publish path fails open by design. Adding a hop in front of that changes the failure rate, not the failure behaviour — so the canary can prove the router under real traffic while the fallback is being written.

That stops being true immediately afterwards. cnx-cinema's reviewer emails a skip digest and loses a night's QA; familybook and living-chart are batch jobs where a mid-run outage wastes the run. Those want a fallback chain in the client before they depend on a single Worker.

What must be true before starting

  • KV matches git. curl /v1/tiers against tiers.json. True today; it is a manual step, so re-check each time.
  • The app's token is stored where that app keeps secrets — a wp-config.php constant for route1views, /root/.secrets.env on the VPS for cnx-cinema, .env for Python. Never in the repo, never in a docroot.
  • The old path stays intact and reachable behind a flag for every migration. Every rollback below is "flip the constant back", which only works if nothing was deleted in the same change.
  • Deletion is a separate, later commit than the cutover. Migrate, run for a week, then delete.

Per-app plans

1 · route1views canary

What it does today

Three call sites, all through one class, all JSON mode, none streaming, none vision: CreatorHelpersController (title + content suggestions, AJAX, includes nopriv guests), CreatorController::getAiCategorySuggestions (AJAX, nopriv, no rate limit), and SpamScoreService::classify() (synchronous on the publish path, fails open). All resolve to provider compat + model dynamic/low — a Cloudflare Dynamic Route that already does Google→Azure→Anthropic failover server-side.

What changes

  • LlmService keeps its public API exactly — complete() still returns the OpenAI-shaped envelope and still returns null on failure. Only its private buildUrl/buildHeaders/buildRequestBody/parseResponse internals are re-pointed at /v1/chat, mapping the router's {text, model, usage} back into that envelope. Nothing above the class knows.
  • setContext() → logUsage() → AiUsage::record() keeps working: the router returns both model (the link that actually answered) and usage, which is exactly what the cost ledger reads today.
  • Two new constants: R1V_LLM_ROUTER_URL and R1V_LLM_ROUTER_TOKEN. R1V_LLM_MODEL becomes R1V_LLM_TIER = low.
  • The bundled LlmTiers.php gains json_mode and max_completion_tokens — the content path calls setMaxTokens(8000) and the router would otherwise silently cap it at 4000.
  • SpamScoreService's setSystem() becomes a {role:"system"} message. Safe on the Azure links; see the risk note.
  • Out of scope, do not touch: OpenAiModerationService (moderation endpoint), FalAiService (images/video), and docs/seo/site-graph/embed_views.php (WP-CLI embeddings). These use AiGatewayService directly and the router has no equivalent for two of the three.

What gets deleted

Nothing at cutover. In a later commit, once it has run a week: LlmService's per-provider branches (parseAnthropicContent, the google-ai-studio and anthropic URL/body shapes, the response-shape sniffing at line 229) — roughly half the class. The gpt-4o-mini legacy row in AiCreditsService can go at the same time. AiGatewayService stays — moderation, fal and embeddings still need it.

Risk low

  • The AJAX helpers are guest-reachable and one of them has no rate limit. The router adds a hop but the token is server-side and never reaches the browser, so exposure is unchanged.
  • The system message is the only real behavioural unknown: if the chain falls through to the Anthropic link, a system role is invalid in that dialect and the link fails. That is a fail-open spam check, not a broken page — but it is the thing to watch.
  • TIMEOUT = 30 now covers two hops. Worth raising to 45 on the content path.

How to verify

There is no test harness for this code — no WP-CLI command, no test references LLM at all — so verification is wp eval on DDEV plus the browser:

ddev wp eval 'var_dump(Route1Views\Support\SiteConfig::llmTier());'
ddev wp eval '$l=new Route1Views\Application\Services\LlmService();
              var_dump($l->setContext("spam_score")->complete("Return JSON {\"ok\":true}"));'
ddev wp eval 'var_dump(Route1Views\Application\Services\SpamScoreService::analyzeView(<postId>));'

Then drive the /create/ wizard with the route1views skill's auth-cookie harness and watch wp-content/debug.log for the LLM: Response received in Xs lines. Confirm in the Cloudflare AI Gateway log that the calls now carry {"project":"route1views"} and that AiUsage rows still record a real model id rather than the tier alias.

Rollback

Set R1V_LLM_MODEL back to dynamic/low in wp-config.php. No deploy, no code change — the Dynamic Route is untouched and still live. This is why the deletion commit must come later.

2–3 · aigw.py, the shared Python client

What it does today

357 lines, of which ~150 build provider chains locally from a bundled tiers.json. Eight consumer repos import it: og-studio (achat), familybook (chat ×4 with images= and temperature=, plus embed ×3), living-chart (3 scripts, bulk), front-door (optional import, bulk), helloplaydate/scripts/build_pin_spec.py (bulk), and this repo's own selftest.py and stress.py.

What changes

  • chat / achat / embed / aembed keep their signatures and their return contracts — including json_mode=True returning a parsed dict with the markdown-fence salvage. Only the body becomes POST /v1/chat and POST /v1/embed.
  • New env var LLM_TIERS_TOKEN; CF_AIG_TOKEN, CF_ACCOUNT_ID and AZURE_RESOURCE stop being needed by the client (they remain needed by anything calling the gateway directly).
  • Do this in two waves. Wave A is every plain-text caller — living-chart, front-door, the build-pin script, og-studio. Wave B is images= and temperature=, and cannot start until the Worker supports both; today a temperature is silently dropped and a vision call only works if Azure happens to answer.
  • _DEPRECATED_TIERS (offload→bulk) moves into the Worker, or gets a removal date. It is cruft on a timer either way.

What gets deleted

  • build_chain, _element, _endpoint, _headers, _extract_text, the module-level _SPEC/TIERS load — about 150 lines.
  • profiles, PROFILES, _ordered() and the profile= keyword. Confirmed dead. A grep across ~/Projects and ~/Sites finds exactly three mentions outside aigw.py itself: two in scripts/selftest.py, which tests the feature and nothing else, and one line of README. No application anywhere passes profile=. Delete the feature, its selftest block, the README line, and the profiles object in tiers.json — but keep the policies block, which is the same idea done properly and is the intended replacement.
  • The chain tables restated in README and the using-llms / offload skill docs. Replace with "ask /v1/tiers".

Risk medium

Not from any one call site — from the count. Eight repos share one file, and if the wrapper changes a return contract subtly (a dict where a string was, an exception type) it breaks all eight at once, in scripts that mostly run unattended. The mitigation is that the public signatures do not move, and that TierError stays the single exception type.

The specific trap: familybook passes temperature=0.1 and 0.2 deliberately. Migrating it before the Worker accepts temperature would silently return non-deterministic output from a call site that asked for near-determinism — a regression with no error attached to it. Hence the two waves.

How to verify

python3 scripts/selftest.py is the harness and already checks json_mode, vision and embeddings across every tier, plus reads the gateway log back to see which provider actually answered. Run it before and after and diff. Then re-run one real job per repo against known input — living-chart's audit_coords.py and familybook's bias.py are the two with the most distinctive output shapes.

Rollback

git revert in ai-gateway-tiers, then reinstall (pip install -e client) in each consumer. No consumer repo changes at all in wave A, so there is only one thing to revert. Keep the deleted chain-expansion code recoverable in git history rather than trying to keep both paths live in the file.

4–5 · cnx-cinema

What it does today

services/LlmService.js reads a vendored services/tiers.json at import time and builds the gateway attempt array itself. The vendored chains are, checked today, byte-identical to the canonical file — the drift is in the surrounding doctrine (policies, capabilities, routes, profiles are all missing), not the models. Two real callers:

  • enrichment/tmdb.js — title identification fallback, tier low, plain text out, own JSON parsing, no tools. Returns null on any failure and the pipeline continues.
  • enrichment/reviewer/index.js — the nightly QA reviewer, tier high, a system prompt, TMDB function tools, up to 16 tool rounds, one retry on an unparseable reply. Because tools is set, buildChain drops the Google and Anthropic steps, so this path is effectively Azure-only already.

What changes

  • Step 4: tmdb.js's askLlm calls the router. Fifteen lines of fetch. LlmService.js stays exactly as it is for the reviewer.
  • Step 5, later: the reviewer moves only once /v1/chat can carry tools, tool results and a system prompt across rounds. Until then it is the reason the file exists.
  • Env: add LLM_TIERS_TOKEN to /root/.secrets.env on the VPS. While in there — .env.example is badly stale (it still documents GEMINI_API_KEY and LLM_ROUTE=gemini-flash-lite) and omits AZURE_RESOURCE, which isConfigured() requires. If that variable is missing on the box the reviewer skips silently. Worth fixing in the same pass.

What gets deleted

Not at step 4. services/tiers.json and the whole of buildChain/buildElement/extractMessage can only be deleted after step 5, because the reviewer needs them. Deleting the file at step 4 — as the architecture review's cruft list implies — would take the nightly QA offline. At step 5 the deletion is the whole file plus roughly two-thirds of LlmService.js.

Risk

medium for step 4: the caller already treats null as routine, so the worst realistic outcome is TMDB fallback identification stopping — degraded enrichment, not an outage. The real cost is the deploy shape: this runs in a Docker container on the pressive.in VPS, auto-deployed on push to master, and services/ is COPY-ed into the image. Every change is a rebuild, and rollback is a redeploy rather than a config flip.

high for step 5: a 16-round tool loop reimplemented behind an HTTP boundary is a genuine rewrite, on the path that produces the QA digest. Do not attempt it as part of this migration.

How to verify

# cheapest — resolves the tier and prints the chain, no network
node -e "import('./services/LlmService.js').then(m=>console.log(m.getModel('reviewer'), m.isConfigured()))"

node enrichment/reviewer-sandbox/loop-test.js     # offline, no keys
bash scripts/smoketest.sh                          # the CI gate
node enrichment/reviewer-sandbox/run.js            # 8 fixtures, live LLM, in-memory DB
node enrichment/reviewer/cli.js --dry-run          # prod data, no writes, no email

Note that npm test does not cover the LLM path, and the /health endpoint passes with a completely broken gateway config. Neither is a valid check here.

Rollback

Revert the commit and let the master-push Action redeploy; or on the box, git checkout the previous ref and docker compose up -d --build. Budget minutes, not seconds — which is another reason this is not the canary.

— · helloplaydate do not migrate

The premise was that its justification had expired. It has not. The decision doc does not say "attribution by project" — it says per-user attribution, and that is what the code does. The Worker forwards {project: <app>} only, and when a per-app token is used it overrides whatever the caller sends. There is currently no way to carry a user_id through it.

What is actually riding on the current implementation

  • Per-user attribution. cf-aig-metadata carries request_id, user_id or a truncated salted ip_hash, booklet_id, plus kind/tier/model per link — bound from an ambient contextvar in app/main.py and app/services/jobs.py. A guard test asserts the header literal appears in exactly one module. Losing this is losing the ability to say which customer cost what.
  • The gate tier. Deliberately Anthropic-Haiku-first against an otherwise universal Azure-first policy, because four modules carry numeric thresholds fit to Haiku's output distribution — likeness_gate (HAIR_MIN 0.55, SKIN_SEVERE 0.25, OVERALL_MIN 0.55, ANCHOR_OVERALL_MIN 0.62 with AUC-derived weights), identity_check (IDENTITY_MIN 0.66 — "the knee of an ROC table", ANCHOR_IDENTITY_MIN 0.70, AGE_GAP_HARD 4.0), face_check, and vision_meta's model-keyed price table. All of these degrade open, and the entire test suite feeds canned replies — so a re-route that breaks them returns 200, passes every test, and is invisible until a customer receives a whitewashed or wrong-child render. Do not touch this tier.
  • Things the router has no field for: per-link timeouts (the stated reason a gateway-side route was rejected), BYOK retry on 401/402/403 with a provider-scoped key whitelist, json_mode treated as a failover criterion rather than a request flag (a 200 carrying prose counts as a failed link), temperature with a per-model _REJECTS_TEMPERATURE exclusion table, normalised token usage feeding a persisted cost ledger, batched embeddings, a runtime assertion that bulk stays Azure-only, and two test seams that seven business modules depend on.
  • Missing tiers. KV has no gate and no transcribe.

What would have to be true to reconsider

  1. /v1/chat accepts an arbitrary per-call metadata object and merges it into cf-aig-metadata alongside the token-derived project — with the same privacy contract the app enforces today (no raw IP, no email, size-capped).
  2. gate and transcribe exist in tiers.json, with gate keeping its Anthropic-first order and a comment explaining why it violates the house policy.
  3. temperature, system, images and per-link timeouts are supported.
  4. The calibrated gates have been re-measured against whatever leads the chain — the bakeoff the decision doc records as deferred, not done.

That is four prerequisites, one of which is a measurement campaign against corpora that partly do not exist. The natural moment is the credit cliff around 21 Sep 2026, which the decision doc already names as the review point. Until then the honest answer is that helloplaydate's implementation is not duplication — it is a superset, and the router is the thing that is missing features.

What can be done now, cheaply

One thing only, and it is not a migration: scripts/build_pin_spec.py imports the shared aigw client for a bulk call. That rides along with the aigw.py work in step 2 and touches none of the above.

Recommended first move

route1views. It is the only consumer where every call site already treats an LLM failure as a normal outcome, so a router outage during the canary period degrades UX instead of breaking a flow — which is what makes it safe to run ahead of the client fallback. It is three call sites behind a single class, so the change is contained. Rollback is one constant in wp-config.php with no deploy. And it is the consumer that proves the thing the router was built for: a PHP app naming a tier, which was impossible before.

Give it a week of real traffic before deleting anything, and use that week to write the client fallback chain that everything after it should depend on.
