The tier system

Architecture review — 8 August 2026 · is it maximally versatile, and is it elegant?

Apps should never name a model. They should name a job — and something else should decide which model does it. That's the whole idea. Everything below is about how close we actually are to it.

Explain it like I'm five

You don't order a specific chef. You order a kind of meal.

An app says "this is bulk work" or "this is hard work" — and never says gpt-5.6-luna. A dispatcher looks up who's on duty for that kind of work, sends the job to the first cook, and if that cook is busy, passes it to the next one down the list. The app never finds out, and never needs changing when the roster changes.

The list of who's on duty lives in one place. Change it there and every app in the world obeys the next second — no code edits, no deploys.

Where we started, and why it hurt

Until today the tier list was bundled into the code. That's fine with one consumer. We have four, in three languages, so the same table got copied four ways and drifted:

Three symptoms, all real and all found today:

  • A one-line policy change meant editing three files in three repos.
  • The two PHP apps could never participate at all — the client is Python — so they pinned models by hand and rotted. gpt-4o-mini is a 2024 model.
  • Nothing enforced agreement. Drift was silent.

The request an app makes is now the entire interface:

POST /v1/chat
{ "tier": "bulk", "messages": [ … ], "project": "kboodle" }

→ { "text": "…", "model": "gpt-5.6-luna-2026-07-09", "ms": 941 }

No model id. No provider. No API key. Any language that can POST JSON is a first-class citizen — which is what finally lets the PHP apps in.

Is it elegant?

Elegant in shape, not yet elegant in fact — because we now have two implementations of the same idea running side by side:

That's the main blemish. Two code paths that must agree, plus a manual sync step between git and KV — which is exactly the class of problem this project set out to delete.

The honest defect list

#IssueSeverity
1No client fallback. If the Worker is down, every app that uses it is down. Each client needs a hardcoded chain to fall back to.must fix
2Manual git→KV sync. sync.sh is a human step, so git and live can silently disagree. Should run on push.should fix

7Nothing migrated yet. All four apps still run the old way; the Worker has no production traffic.pending

  • ~150 of 357 lines of aigw.py — everything that builds a provider chain locally. The client shrinks to "POST tier + messages, return text".
  • cnx-cinema's copied tiers.json — deleted outright, not synced. This was the whole reason it existed.
  • helloplaydate's re-implementation. Its documented justification was per-user spend attribution via its own gateway — the Worker now forwards project into cf-aig-metadata, so that reason has expired. Worth re-deciding rather than assuming; its gate tier is genuinely bespoke and calibrated.
  • Chain tables restated in three prose docs (README, using-llms, offload). Once KV is authoritative these are copies that can only drift — they should say "ask /v1/tiers" instead of listing models.
  • The offload→bulk deprecation shim — harmless now, but it is cruft on a timer. Give it a removal date.

The pattern worth noticing: almost every item here is a copy of the truth rather than the truth — a duplicated table, a restated chain, a cached measurement. That is the same disease the Worker cures, so adopting it and then leaving these in place would be the worst outcome: one more copy, not one fewer.

Verdict

Versatility: strong, with three named holes. The language barrier — the thing that actually broke the system — is gone. Embeddings, images/video and streaming remain outside.

Elegance: the design is right, the implementation is halfway. One dispatcher, one table, dumb clients is the correct shape. But two chain-expanders and a manual sync are precisely the duplication the project exists to remove. It isn't elegant until the Python client stops expanding chains and KV updates itself from git.

The shortest path to "yes" on both

  1. Fallback chain in every client — removes the single point of failure. Nothing else should ship first.
  2. Auto-sync KV from git — a GitHub Action on push to tiers.json. Deletes defect #2 permanently.
  3. Make the Python client a thin wrapper over /v1/chat — collapses two implementations into one.
  4. Add /v1/embed — closes the one gap where a tier is promised but not delivered.
  5. Per-app tokens in KV — real attribution and revocation.
  6. Streaming and image/video routing only if a real product needs them. Don't build on spec.
