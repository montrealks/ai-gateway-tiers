The whole estate

Integration map — 8 August 2026 · every surface that calls a model, and what the router must grow to take it

The migration plan looked at four consumers. A grep across ~/Projects and ~/Sites finds twenty-one repos containing sixty-one distinct model-calling surfaces. The four in the plan account for eleven of them. This document is the other fifty — and the honest news is that only a quarter of the estate is blocked by anything interesting. Most of it is blocked by temperature.

The headline number. Of 61 surfaces: 17 can migrate (4 of them today, with no router change at all), 25 are blocked on a named router gap, 13 must stay separate for a good reason, and 6 are dead code that should be deleted rather than migrated.

Two thirds of the blocked set are waiting on two gaps: vision image input (10 surfaces) and tool calling (7). Nothing else blocks more than five.

This extends migration-plan.html and fallback-plan.html rather than repeating them. Where a surface is already covered there, the row says so and moves on. Everything else is new.

Vision is the single highest-leverage gap. Ten surfaces across seven repos wait on roughly thirty lines of per-provider content mapping — more than tools, image params and temperature combined, at a fraction of the cost of tools. It is also the gap with the nastiest current failure mode: vision does not error today, it works only when Azure answers, which means every vision caller in the estate is silently pinned to a credit pool that expires around 21 September 2026.

What is deliberately not a gap

  • Video. capabilities.video.failover is opt-in-only — sora-2 → MiniMax is a permission escalation, not a quality ladder. video-gen's Modal path and sora-tests stay off the router by design, not by omission.
  • Speech / TTS. Four surfaces (video-gen ×3, media-factory) produce binary audio from SSML with callback events. Out of scope; nothing about them is a tier decision.
  • Image embeddings. familybook's open_clip and media-api's 512-d face vectors are local/RPC compute. The embed capability's same-model-different-provider-only contract makes routing them actively dangerous.
  • Self-hosted inference. kamasutra's FLUX-on-ComfyUI and video-gen's LTX/Wan run weights Kris owns on GPUs Kris rents. There is no provider to fail over to.

The sequencing rule that matters more than the order. The fallback plan's finding holds for all fifty new surfaces: do not delete the existing path when you wire the router in front of it — demote it. Every one of these call sites already contains a working, router-independent route to a model. Doing this now costs one try/except per client; doing it after migration costs rewriting code that was deleted.

Two properties of that picture are worth stating out loud. First, the router never becomes the only path — the KEEP SEPARATE column is thirteen surfaces wide and is meant to stay that way, because each of them is separate for a reason that does not expire. Second, everything Kris pays for that is not on the router today is billed to Azure credits with a September expiry: living-chart's direct client, video-gen's image path, media-factory, familybook, and every vision caller in the estate by accident. The credit cliff is not a helloplaydate deadline. It is an estate-wide one, and this inventory is the list of what has to be repointed when it arrives.
