Fallback resilience for the router

Plan — 8 August 2026 · what happens to every app when llm-tiers is down

The router is a genuinely good idea that introduces exactly one genuinely bad property: every app now depends on one Worker. This is the plan to keep the good property and delete the bad one — without putting provider keys back into application code, and without building anything that needs maintaining.

First, the thing that changes the whole shape of the problem

Nothing in production calls the Worker yet. Verified by reading the clients:

  • client/aigw.py — builds chains locally and POSTs the Cloudflare universal endpoint. Never touches the Worker.
  • cnx-cinema/services/LlmService.js — vendored tiers.json, universal endpoint. Never touches the Worker.
  • route1views PHP LlmService — provider compat, model dynamic/low, i.e. a gateway-side dynamic route. Never touches the Worker.
  • helloplaydate/app/services/ai_gateway.py — its own TIERS table, its own gateway, its own per-link retry loop, for per-user spend attribution. Never touches the Worker.

The only live Worker consumers are the ad-hoc tokens (claude-code, video-gen). So the single point of failure is prospective, not current — it arrives the moment these four are migrated.

That reframes the work completely. This is not a rescue operation bolting resilience onto a live dependency. It is a migration rule: when you wire a client to the router, do not delete the code that is already there — demote it. Every client already contains a working, tested, router-independent path to a model. The fallback layer we need has already been written four times. The migration's job is to stop treating that code as something to remove.

Doing this now costs one try/except per client. Doing it after the migration costs four rewrites of code that was deleted.

Q1 — Which layer should the fallback live in?

Rejected: a second Worker

A twin Worker shares everything that actually breaks. Same Cloudflare account, same KV namespace, same CF_AIG_TOKEN secret, same tokens key. Enumerate the realistic failures of llm-tiers:

FailureLikelihoodDoes a twin Worker help?
Bad deploy of src/index.jsHigh — it's a hand-edited 319-line fileOnly if the twin runs an older commit, which is a second thing to keep alive
sync.sh writes a broken/partial tiers KV keyMediumNo — shared KV
CF_AIG_TOKEN expires or is rotatedMediumNo — shared secret
An app token gets revoked / tokens key mangledMediumNo — shared KV
Cloudflare Workers platform outageVery lowNo — same platform

A twin covers roughly none of the probability mass. Reject.

Rejected: DNS or Load Balancer failover

Costs money, adds a config surface with no version control, and fails the same table above — both pools sit behind the same script, KV and secrets. You also cannot meaningfully improve on Cloudflare's own availability using Cloudflare. Reject.

Accepted: in the client

The client is the only layer that can tell the difference between "the router is broken" and "the model is unreachable" — and it is the only layer that already has a second route to a model. It is also the only layer under the app's own control at the moment of failure.

Be honest about what this does and does not buy. The client's fallback target is the Cloudflare AI Gateway — also Cloudflare. If Cloudflare is down wholesale, no fallback short of a provider API key baked into the app will save you, and that key is precisely what this entire system exists to delete. So: this plan covers router-specific failure — my bug, my bad deploy, my KV, my token — which is essentially all of the real risk. It does not cover a Cloudflare-wide outage, and we accept that. Do not put Azure or Anthropic keys back into app code to close that last gap; the cure is worse.

Q2 — Fall back to what?

OptionCode costDrift riskVerdict
(a) Universal endpoint with a baked-in chain ~40 lines per language — but already written in Python and JS Moderate, and bounded: a stale chain still answers, it just answers with an older model Yes for Python + JS
(b) One hardcoded model ~10 lines Worst of the three. Low drift mechanism, high drift consequence: the table's own _model_churn note says Azure deployments come and go, so a pinned deployment name is one deprecation away from a fallback that also fails. And it re-introduces a model id into app code, which is the law this system exists to enforce. No
(c) A gateway-side dynamic route (compat + dynamic/low) Two strings. No chain in code at all. Lowest — the chain is maintained at Cloudflare, not in the app. Caveat: Azure cannot be a dynamic-route step (no place for resource/api-version), so the route is Google-first with a paid tail. For a fallback that is fine, and it matches the existing client profile policy anyway. Yes for PHP
(d) Client caches the live tier table off /v1/tiers A cache surface, an invalidation story, and a new Worker endpoint — /v1/tiers currently returns only provider:model strings, not the full step shape (resource, path, params) needed to rebuild a chain Lowest in theory Not now — solves a drift problem we are about to argue doesn't exist

Recommendation: the fallback is per-language, and it is the code that's already there

  • Python (aigw.py) — it already contains build_chain(), the per-provider wire-format expander, and _post() against the universal endpoint, and it already ships tiers.json in the package. Its fallback costs an if. Make the Worker primary; keep the existing 200 lines as the fallback path.
  • JS (cnx-cinema/services/LlmService.js) — identical situation, with its own vendored services/tiers.json. Same move.
  • PHP (route1views, profilo) — do not port the chain expander into PHP. Fall back to dynamic/low via the existing AiGatewayService, which is what route1views does today and what already works in production.
  • helloplaydate — leave it entirely alone. It needs per-user spend attribution on its own gateway, which the router does not model. Migrating it is a separate decision; it is not a source of SPOF risk today.
  • kboodle — out of scope by rule (client's own CF account, must never touch the router).

Q3 — How does a client know the router is unhealthy, and how does it recover?

Do not probe /health

Two reasons. First, a probe doubles the latency of every call and adds a failure mode of its own. Second — and worse — /health currently lies. Read the Worker: the /health branch returns {ok:true} on line 122, before the auth check and before the KV read on line 127. So the most likely real failure — a missing, empty or corrupt tiers key after a bad sync.sh, or a stale CF_AIG_TOKEN — reports perfectly healthy. Fix that (read KV, assert tiers.low.chain is a non-empty array) and point an uptime monitor at it. Clients should still not probe.

Use the failure of the real call

The signal is the response to the request you were making anyway:

  • Fall back on: any transport error or timeout; HTTP 5xx; HTTP 401/403 (token revoked → the router is misconfigured for us); HTTP 429 from the router itself.
  • Never fall back on HTTP 400. "unknown tier", "messages[] required", "unknown route" are our bug. Falling back would mask a code error as a transient outage, and you would ship it.
  • Timeouts: a short connect timeout (~3s) plus a generous read timeout (the existing 180s). A single total timeout can't distinguish "the Worker isn't there" from "the model is thinking", and generation genuinely takes minutes.

Recovery: try again next call

No circuit-breaker library. Most of these callers are short-lived — a CLI script, a PHP request — and a breaker has nowhere to live in them. For the two long-running processes it is worth about five lines: a module-level _router_down_until timestamp, set to now + 60s on a fallback, checked before the router call. That is the entire circuit breaker. No dependency, no half-open state machine.

Log every activation loudly, with a distinct greppable prefix (llm-tiers FALLBACK:). Silent degradation is how you discover in November that the router has been down since September and everything has quietly been running on the paid tail.

Q4 — How does the baked-in fallback stay current? the crux

It doesn't, and it shouldn't try. Optimise the fallback for durability, not fidelity.

The instinct is to keep the fallback chain in sync with the tier table, which recreates exactly the N-copies drift the router was built to delete. The way out is to notice that a fallback chain and a primary chain want different things.

Look at where the churn actually is. The head of every tier is Azure deployments — gpt-5.6-luna, gpt-5.6-terra, DeepSeek-V4-Flash-dz — names that are specific to one Azure resource, need an api-version, and (per the table's own _model_churn and _deployment_capacity notes) get created, renamed and retired constantly. The tail is gemini-3.6-flash and claude-haiku-4-5-20251001: real, public, versioned vendor model ids on stable APIs, which have been stable and will still resolve in six months with zero maintenance.

So the fallback chain should be the tail, not the head — two steps, deliberately boring, deliberately not a copy of the tier table:

fallback.low   = [google-ai-studio:gemini-3.6-flash, anthropic:claude-haiku-4-5-20251001]
fallback.high  = [google-ai-studio:gemini-3.1-pro-preview, anthropic:claude-sonnet-5]
fallback.embed = [azure-openai:text-embedding-3-small]   # same model only — see Q5

Three consequences, all good:

  • It isn't a copy, so there is nothing to keep in sync. Nobody is tempted to mirror a model swap into four places, because the fallback deliberately doesn't contain the models that swap.
  • Stale is cheap. This chain fires only during a router outage, and the cost of it being a generation behind is a slightly worse answer, not an error.
  • Cost inversion is acceptable. The tail is the Google free tier then Cloudflare unified (paid). During an outage that is the correct trade, and it is the same policy the client profile already applies deliberately to production client sites.

The drift control is an assertion, not a sync

Add one check to scripts/selftest.py: every model named in any client's fallback must still appear somewhere in tiers.json, and each capability's fallback behaviour must match its declared failover field. That catches genuine rot (a model that has left the estate entirely) without demanding that anything be mirrored. Review cadence becomes ~2 events a year — the next one is the Azure credit expiry around 2026-09-21, when the whole chain is being revisited anyway.

Where does the fallback list live? In tiers.json, under a top-level fallback key. Python and cnx-cinema already vendor that file, so it travels with the package and is naturally "roughly current" with no mechanism at all. PHP doesn't read it — PHP's fallback is the dynamic/low string.

Q5 — Per-capability contracts

The table already states the contracts in capabilities.*.failover. The fallback layer should read that field rather than hardcode behaviour per endpoint — that way a new capability inherits correct handling for free.

CapabilityfailoverFallback behaviour
chat free Full durable tail chain. Nobody cares which model answered.
embed same-model-different-provider-only The fallback is not a chain — it is the same single step, one hop shorter. The embed tier is already a one-link chain (text-embedding-3-small); the fallback calls that exact model on the universal endpoint directly. If it is unreachable, raise. Never substitute.
image / image-edit within-look-only No fallback in v1. The Worker deliberately has no chain here — a style swap mid-batch is worse than a loud failure, because it is silent. A failed batch is rerunnable; a stylistically mixed batch is not detectable without a human eye.
video opt-in-only No fallback, ever, automatically. It is a permission escalation, not a quality ladder.

Make the embed contract impossible to violate, not merely unlikely

Both the router path and the fallback path should assert the response's model and dims against what was expected, and raise on mismatch. That is about four lines and it converts "a silent wrong-vector-space corruption of the index" into "a loud error at write time". Given that a corrupted index is discovered months later by search quality quietly going bad, this is the highest-value four lines in the plan.

If image fallback is ever added

Resolve the model once per batch and pin it for the whole batch — never per item. Per-item resolution is precisely how you get a set that is half one look and half another.

Q6 — Minimum viable version

The MVV is a rule, not a feature: when migrating a client onto the router, keep its existing direct path as the except branch.

Because no production client calls the Worker yet, the smallest change that removes the single point of failure is not writing the SPOF in the first place. Per client that is one try/except around the router call, falling through to code that already exists and already works.

If you shipped only steps 1–3 below and nothing else, the SPOF would be gone for every client that matters.

Ordered task list

  1. Make /health tell the truth. In src/index.js, move the /health branch below the KV read and have it assert the table parses and tiers.low.chain is a non-empty array; return 503 otherwise. Then point an uptime monitor at it. ~5 lines. Without this, the monitor is decorative.
  2. Add a fallback key to tiers.json — the durable tail-weighted chains from Q4, plus a one-paragraph _what_this_is explaining that it is deliberately not a mirror of tiers and must not be kept in sync. Run sync.sh.
  3. client/aigw.py: router primary, existing code as fallback. Add a _via_router() that POSTs /v1/chat; route chat/achat through it; on transport error / 5xx / 401 / 403 / 429 (never 400) fall through to the existing build_chain() + _post(), built from fallback rather than tiers. Same for embed, but with the same-model rule and the dims/model assertion. Split the timeout into connect + read. Add the five-line _router_down_until. No new dependency; no new credential (CF_AIG_TOKEN is already required).
  4. Assertion in scripts/selftest.py: every model in fallback still appears somewhere in tiers; every capability's fallback behaviour matches its declared failover. This is the entire anti-drift mechanism.
  5. cnx-cinema/services/LlmService.js: same demotion. Router primary, the existing universal-endpoint path as fallback. Rewrite the header comment of services/tiers.json to say "fallback table — deliberately stale, do not sync", so the vendored copy stops looking like drift and starts looking like a decision.
  6. PHP (route1views LlmService.php, then profilo): when wiring to the router, add the router as a branch in front of the existing AiGatewayService call and keep compat + dynamic/low as the catch. Do not port the chain expander to PHP. Ship the examples/LlmTiers.php helper with the fallback branch built in so both sites get it identically.
  7. Log and watch. One greppable prefix on every activation. Check it once a month; if it fires while the router is up, the health signal is wrong and needs tightening.
  8. Leave helloplaydate and kboodle alone. helloplaydate already owns a per-link retry loop on its own gateway for per-user attribution and is not a SPOF risk; kboodle is exempt by rule.

Explicitly out of scope

  • A second Worker, a load balancer, or DNS failover — they share the failure domain (Q1).
  • A circuit-breaker library, retry framework, or service mesh.
  • Provider API keys in application code, for any reason, including "just for the fallback".
  • Image or video fallback — loud failure is the contract (Q5).
  • Client-side caching of the live tier table (option d) — revisit only if the durable-tail approach is measured to be insufficient, which it won't be.
